# AGENTS.md

Guidance for coding agents working on shroudlink: a mod framework for Enshrouded 1.0
dedicated servers, and chestsort, the mod it ships with. Read `README.md` for what it
does, and `mod/MODDING.md` for the protocol, the plugin API and lessons about the
game's UI.

## Layout

| Path | What |
|---|---|
| `mod/` | Rust workspace (Windows x64 only) |
| `mod/server` | `chestsort.dll`, installed on the server as `steam_api64.dll` (a proxy; the original is renamed `steam_api64_o.dll`). Deposit hooks, categories, locks, shroudlink host, plugin loader |
| `mod/client` | `shroudlink_client.dll`, installed next to `enshrouded.exe` as `dinput8.dll`. Native UI (MODS tab, chest search, slot locks), input, channel |
| `mod/link` | Wire protocol: `~sl1~` + base64url packets of at most 256 chars, frames, chunking, declarative UI types |
| `mod/sdk`, `mod/examples/hello_mod` | C-ABI plugin SDK (`shroudlink_mod_v1`) and an example plugin, loaded from `shroudlink_mods/*.dll` |
| `mod/common` | Logging, signature scanning, DirectInput proxy |
| `mod/eml` | EML (Lua) data mods: chests x2 slots, stacks x10 |
| `mod/server/categories.json`, `items.tsv` | Default categories and the item id → debug name table for the current build, generated by `research/scripts/categorize.py` |
| `dist/chestsort-enshrouded/` | Server-owner package: `UPDATE-SERVER.bat/.ps1`, `repatch/` |
| `research/scripts/` | Reverse-engineering helpers (see below) |

Everything else in the working folder (game installs, dumps, saves, Ghidra projects) is
deliberately ignored by the whitelist `.gitignore`. Never add game binaries, dumps,
savegames, `emm.exe` (EML is GPL-3.0 and is downloaded at runtime) or credentials.

## Build and test

```
cd mod
cargo build --release          # target/release/chestsort.dll + shroudlink_client.dll
cargo test -p chestsort-server  # protocol, chunking, chestsort UI, plugin round trip, locks
```

- There are no automated tests against the game. Verify in game, and say so when you
  could not.
- **Client dev loop:** `python research/scripts/inject.py enshrouded.exe mod/target/release/shroudlink_client.dll`
  hot-reloads the addon into the running game; the new copy shuts the old one down.
  Logs go to `shroudlink_client.log` in the game folder. `research/scripts/shot.py <out.png>`
  takes a screenshot of the game window.
- **Server dev loop:** run a local dedicated server, copy `chestsort.dll` over its
  `steam_api64.dll` and restart it (there is no server hot reload). The log is `chestsort.log`.
- An installed DLL that the running game has loaded cannot be overwritten. Rename it
  (`dinput8.old.dll`), then copy.

## How the game code is found

- Every hook point is located by a **byte signature** (`SIG_*` constants) at the function
  entry. Helpers are found as the n-th `call` inside a signed function (`call_targets`),
  which survives patches better than signatures for small functions.
- After a game update, check that every `SIG_*` still matches exactly once in the new
  exe before anything else. Use `mksig.py` to make new signatures.
- Struct offsets come from the game's reflection data (`kfc-parser extract-types`, then
  `reflect.py`) and from Ghidra (`ghidra.sh DecompileAt.java <outDir> <addr>`).
  Document an offset where it is used, with the type and field name (see `game.rs`).
- Tools: `disasm.py` (one function), `ripxref.py` (fast xrefs), `memscan.py` (live
  strings), `dumpmod.py` (dump the DRM-unpacked client for Ghidra; the client base differs
  per run).

## Facts that are easy to get wrong

- **Client and server share ECS entity ids** within a session, but ids change between
  sessions. A slot id is `entity | slot_index << 32`. Persist positions, not ids
  (see `client/src/locks.rs`).
- `FUN_1401ad1c0(out, ctx, a, b, ...)` (quick stack / deposit) runs in **both
  directions**: chest → player too. Check `Game::is_player` before treating an argument
  as the player. The R button ("move all") is a separate function, `FUN_1401ad940`.
- Vanilla deposit skips empty stacks; locked or equipped stacks are hidden from it by
  zeroing their count for the duration of the call and restoring it afterwards.
- UI: frames need unique keys (`UiStr::keyed`) and explicit sizes; widget clicks use
  our own hit testing on layout rects (node+0x114, 1080p UI units); the text input
  subclasses the game's WndProc and must swallow key **downs** only, never releases or
  mouse input (otherwise keys get stuck).
- The user wants UI **embedded** in the game's own panels, not floating windows.

## Safety rules (production server)

- **Never start a server with its world on new-build vanilla data while the save holds
  x10 stacks**: the game deletes everything above the vanilla stack size on load. That
  happened once already. Updates go through `UPDATE-SERVER.ps1`, which parks the world
  while the server updates.
- The EML data patches (`enshrouded_server.kfc`, `.kfc_resources`) are tied to one exact
  build; patched files for build A crash build B. The mod DLL usually survives updates.
- On the host, replace files by rename (`x.new` → `x`, keep `x.prev-*`). Never delete
  anything, and never overwrite savegames. Back up `savegame/` before any change.
- Restarts, uploads and anything public (repo visibility, releases) need the owner's
  explicit go-ahead. Never commit or log passwords.

## Style

- Match the surrounding code: short doc comments that explain *why* or name the
  game type/offset, no narration. Rust 2021, no new dependencies without need.
- User-facing text (READMEs in `dist/`) is written for non-programmers.
- Commit messages: imperative summary line, body explaining why.
